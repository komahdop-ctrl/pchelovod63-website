# ПЧЕЛОВОД 63 — план переноса на российский хостинг

**Дата подготовки:** 25 октября 2026 года  
**Домен:** https://pchelovod63.ru/  
**Текущая публикация:** GitHub Pages, GitHub Actions `.github/workflows/deploy-pages.yml`  
**Статус:** ПОДГОТОВКА; домен, DNS и действующий хостинг **не переключены**. Этот документ не является заключением о полном соответствии 152-ФЗ.

## Решение по архитектуре

Текущий публичный портал — преимущественно **статический Vite-сайт**. Для начального переезда достаточно российского виртуального хостинга: готовые HTML/CSS/JS и изображения загружаются из `dist/`; Node.js, Git, сборщик и публичная база данных на сервере для показа сайта не нужны.

Предварительный кандидат — **Beget, виртуальный хостинг Blog**, при условии письменного/договорного подтверждения размещения конкретного аккаунта и резервных копий на территории РФ. По данным сайта провайдера на дату документа: тариф Blog — 12 ГБ и 420 ₽/мес при оплате за год (5 040 ₽/год), тестирование до 30 дней, HTTPS/SSL, SFTP/SSH. Публичное заявление Beget: виртуальный хостинг размещён в России. Альтернатива: российская площадка Timeweb; проверьте географию выбранного тарифа и фактическую оферту перед оплатой.

## Этап 0. До покупки, смены DNS и любых секретов

- [ ] Установить и документально закрепить, кто юридически является оператором портала и обрабатываемых данных. Не считать автоматически оператором иное ИП/ООО.
- [ ] Получить от выбранного хостинга подтверждение российского размещения веб-сервера, журналов, БД **если будут**, резервных копий и мест техподдержки; проверить договор/поручение по 152-ФЗ и перечень подрядчиков/трансграничных маршрутов.
- [ ] Уточнить юридический статус обработки уже опубликованных имён/фотографий/сведений о пчеловодах: основания размещения, согласия на распространение там, где требуется, право на изображения, сроки/удаление.
- [ ] Проверить необходимость уведомления Роскомнадзора об обработке ПДн, содержание политики, контакты/адрес оператора, меры безопасности и отдельные вопросы трансграничной передачи.
- [ ] Не включать ранее закрытые анкеты, старый чат, сохранение IP в собственной аналитике и прочие формы без отдельного юридического и технического допуска.
- [ ] Не копировать в GitHub или облачные задачи новые реальные анкеты/переписки/телефоны. Публичный GitHub-репозиторий и его история **не переедут автоматически** вместе с сайтом и сами могут содержать опубликованные персональные данные.
- [ ] Сделать независимую резервную копию исходников и содержимого `dist/`; сохранить контрольные суммы и предыдущую рабочую сборку.

## Этап 1. Подготовить хостинг параллельно GitHub Pages

1. Владелец сайта регистрирует хостинг на свои реквизиты, включает двухфакторную защиту, выбирает российский дата-центр/тариф, получает договор/сведения по размещению. **Не присылать пароли, коды или приватные ключи в чат.**
2. Добавить существующий домен `pchelovod63.ru` в панели хостинга, определить **фактический** каталог публикации: `public_html`, `<домен>/public_html` или иной — зависит от провайдера и панели.
3. До переключения домена проверить сайт на техническом поддомене Beget (например, вида `<логин>.beget.tech`, если он предоставлен), либо тестировать через временную DNS/hosts-привязку. При предварительном просмотре не включать индексацию тестового домена.
4. В рабочей копии репозитория собрать сайт:
   ```bash
   corepack enable
   corepack pnpm install --frozen-lockfile
   corepack pnpm build
   ```
   Источник публикации — **содержимое `dist/`**, не корень репозитория. Не загружать `.git/`, `node_modules/`, `*.env`, закрытые документы или секреты.
5. Передавать собранные файлы через панель файлового менеджера или **SFTP**. Для большого набора фотографий можно загрузить архив `dist` и развернуть его в пустом каталоге сайта через защищённую панель. HTTP на тестовом адресе должен открывать именно собранный `dist/index.html`.
6. Убедиться, что `/privacy.html`, `/news/`, `/articles/`, `/apiaries/`, `/events/`, `/opylitel/` и вложенные изображения обслуживаются корректно. Если короткие пути или расширения зависят от конфигурации веб-сервера, настроить это до смены DNS.

## Этап 2. Проверки до переключения домена

- [ ] Домашняя и все разделы без 404/неожиданных 301; проверить мобильную версию и изображения/видео.
- [ ] HTTPS для основного домена и `www` после выпуска сертификата; оба варианта ведут на выбранную каноническую версию, нет mixed content.
- [ ] Ссылка на MAX открывается; уведомление `/privacy.html` и `referrer=no-referrer` сохраняются.
- [ ] Анкеты, ранее закрытые из-за обработки персональных данных, **остаются закрытыми**.
- [ ] Не настроен зарубежный CDN, пиксель, внешняя аналитика или новый хост изображений без отдельного анализа потоков данных.
- [ ] Хостинг выполняет резервное копирование, есть независимые копии и понятный способ отката.
- [ ] Протестировать восстановление нескольких страниц/медиа, не только факт создания бэкапа.
- [ ] Установить правила доступа SSH/SFTP, уникальные пароли, MFA и обновления.

## Этап 3. DNS: только после успешного параллельного теста

1. Выяснить у текущего регистратора **действующего домена** его DNS-провайдера; записать текущие NS, A, AAAA, CNAME, MX, TXT (включая SPF/DKIM/DMARC), CAA. Не менять владельца домена для переезда сайта.
2. За несколько часов/сутки до миграции, при возможности, снизить TTL A/AAAA/CNAME до ~300 секунд и дождаться окончания действия прежнего TTL.
3. Получить **точные IP или DNS-цель** от нового хостинга. Не подставлять примерный IP. Поменять лишь веб-записи `@` и `www`; оставить почтовые MX/TXT и остальные поддомены без изменений.
4. Проверить распространение DNS и работу `https://pchelovod63.ru/`, `https://www.pchelovod63.ru/` с разных сетей и устройств.
5. Убедиться, что и IPv4, и IPv6 записи (если есть) соответствуют новому провайдеру. Старые записи GitHub Pages не должны конфликтовать с сертификатами нового сервера.
6. Если HTTPS сертификат выдаётся после обновления DNS, заранее уточнить механизм валидации и план промежутка; не включать HSTS без достаточной проверки.

## Этап 4. После переключения

- [ ] Повторить тесты живого сайта, SSL, навигации, мобильных страниц и ссылок.
- [ ] Проверить обращение к формам и сохранение запрета на сбор реальных заявок.
- [ ] Настроить регулярные бэкапы в российском размещении и мониторинг доступности.
- [ ] Настроить безопасный процесс обновления: локальная/контролируемая сборка `pnpm build` и загрузка `dist/` на российский хостинг. Для начала можно делать вручную; не добавлять в GitHub Actions пароли сервера.
- [ ] Отдельно принять решение о выводе сайта из GitHub Pages и изменении `.github/workflows/deploy-pages.yml`. Не удалять GitHub Pages заранее: он остаётся временным резервом при переходе.
- [ ] Разобрать сведения/копии в GitHub-репозитории и его истории — смена хостинга не отменяет их наличия за пределами РФ.

## Аварийный откат

При нарушении доступности, SSL или критических страниц вернуть **зафиксированные старые A/AAAA/CNAME** у DNS-провайдера, пока GitHub Pages остаётся доступным; учитывать TTL/кэш DNS. Сохранить копию новой сборки для анализа. Не считать GitHub Pages полноценным резервом после отключения его публикации или удаления настройки домена.

## Что потребуется от владельца для самого переезда

- Действующий аккаунт российского хостинга с тестовым сайтом и подтверждённой локализацией.
- Доступ **самого владельца** к панели DNS/регистратора домена.
- Разрешение выполнить переключение после проверки копии сайта.

**Не приступать к смене DNS без тестового сайта и подтверждения владельца.**
