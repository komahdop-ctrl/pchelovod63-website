## Рабочий процесс

Владелец сообщает, что изменить и нужно ли публиковать. Исполнитель делает изменения в отдельной ветке, проверяет сборку и PR, сливает в main в рамках поручения, ожидает deploy и проверяет живой сайт. Владелец получает ссылку и результат проверки. Браузер Beget для текущих обновлений этого сайта не используется.

Pipeline: build на PR без публикации → build main → архив `site-release-SHA` с SHA256 (30 дней в GitHub Actions) → Pages → проверка реального домена и точного source SHA. Архив содержит только публичную сборку, а не исходные `.env`, секреты или серверные данные. Эта копия в GitHub не заменяет независимый бэкап в другом провайдере.

`deployment.json` содержит источник сборки, время и ссылку на run. Он позволяет отличать новый успешный deploy от старой страницы в кэше. Контрольные пути находятся в `ops/sites.json`. Проверка после деплоя отмечает сбой, но не делает автоматический откат: сетевой сбой может быть временным.

## Откат без ручных кнопок владельца

1. Выбрать полный source SHA из последней проверенной успешной публикации.
2. Через подключённый GitHub изменить `ops/deploy-request.json` в отдельной ветке: `source_sha` = выбранный SHA, `request_id` = уникальная строка.
3. PR-проверка обнаруживает изменение заявки относительно базовой версии и собирает именно выбранный старый SHA. Production на push читает ту же изменённую заявку.
4. Слить проверенный PR. Один pipeline определяет, что изменилась заявка, собирает выбранный старый исходник и добавляет новый маркер, сохраняет архив и публикует.
5. Проверить `deployment.json` и контрольные страницы. История main не переписывается.

После отката исправить main перед следующей обычной публикацией: обычный commit без изменения заявки снова публикует текущий main. Полный SHA обязан быть коммитом в истории репозитория. Если сборка старой версии требует иной версии Node/pnpm, она не пройдёт; не называть такой откат проверенным.

Владелец может выполнить вручную через Actions → Deploy website to GitHub Pages → Run workflow → source_sha. Это запасной путь; обычные команды в чате не требуют этого от владельца.

## Beget и поддомены — ещё не подключены

Панель Beget была проверена в этой сессии и открылась на форме входа. Защищённый вход не завершён. DNS-провайдер домена и актуальные параметры сервера не подтверждены. Основной домен не переключён.

После доступного защищённого входа нужно определить авторитетную DNS-зону, реальный сервер и корневой каталог; проверить предоставляемые Beget технические способы доступа. Для загрузки предпочтителен отдельный ключ с ограничением нужным сайтом. Закрытый ключ хранить в предназначенном для секретов хранилище, не в чате/коде. Не считать API Beget ограниченным по правам, пока это не подтверждено в аккаунте. Поддомен добавлять отдельно, не заменяя записи основного сайта и почты. До включения постоянного доступа показать конкретный объём прав владельцу.

Готовность: GitHub/Pages можно принять только по новому успешному run; Beget, DNS и SSH-доставка остаются pending до настройки и проверки реального доступа. Перенос на российский хостинг не выполнен этой доработкой.
