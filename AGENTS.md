# Управление публикацией по команде владельца

Пользователь ставит задачу обычным сообщением. Если поручение включает публикацию, выполняй подготовку, проверки, PR, слияние и проверку опубликованной версии в пределах уже данного разрешения. Не перекладывай стандартную работу с GitHub на владельца и не проси повторного согласия на уже порученную публикацию.

Перед изменениями читай `ops/sites.json` и `docs/OPERATIONS.md`. Не подменяй фактическое размещение предположением о Beget. Сохраняй действующие проектные ограничения; `EDITORIAL_RULES.md` относится к редакционным материалам.

Используй отдельную ветку и PR, проверь сборку и проверки на точном head SHA. После слияния проверь run, его conclusion, `deployment.json.source_sha` на живом домене и контрольные страницы. Сообщение «готово» допустимо только после этого; коммит и зелёная сборка до deploy не подтверждают публикацию. Для старых версий до появления маркера используй workflow, который добавляет маркер поверх готовой сборки.

Откат делай изменением `ops/deploy-request.json` в main через проверенный PR: полный `source_sha` из ранее успешной публикации и новый `request_id`. Не переписывай историю и не меняй DNS для отката контента. Следующий обычный коммит снова публикует текущий код; для продолжения работы после отката сначала исправь причину сбоя или восстанови нужный контент в main.

Не сохраняй пароли, закрытые ключи, cookies, реальные заявки и закрытые данные в репозитории, логах или артефактах. Не активируй формы. Новые поддомены и Beget требуют отдельно проверенного технического доступа; не заявляй об их настройке до фактической проверки. При входе используй защищённый механизм авторизации. Не обещай бессрочную сессию или отсутствие проверок платформы.

Не добавляй в рабочий деплой незавершённые материалы из соседних веток. В частности, страница Шакуты с двумя отсутствующими треками остаётся отдельным черновиком.
