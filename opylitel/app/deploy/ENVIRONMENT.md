# Российский закрытый стенд r3 — требования и порядок установки

Только вымышленные данные. Это полный переносимый Node/SQLite выпуск, а не подтверждение российского размещения. Переезд НЕ разрешает реальные заявки. Действующий российский контур ещё не проверен. Не устанавливать на основной портал или соседние сайты.

## Требуется от площадки

- Linux x86_64/arm64 и поддерживаемый Node.js24.x с `node:sqlite`, правами запуска постоянного процесса, loopback TCP и остановкой/перезапуском. Встроенный SQLite должен поддерживать RETURNING. Сам Node в архив не включён: системный поддерживаемый бинарник, точная версия фиксируется preflight.
- Nginx с TLS и auth_basic перед ВСЕМИ маршрутами, отдельный подтверждённый тестовый HTTPS hostname; один персональный пароль владельца в отдельном htpasswd. Пароль не входит в конфиг/архив/чат. Владелец площадки создаёт его защищённым способом. Внутренний Node слушает только127.0.0.1, firewall не открывает8787.
- Отдельный системный пользователь opylitel-test, read-only релизы `/opt/opylitel-test/releases/<release>`, symlink current, закрытые `/etc/opylitel-test/config.json`, `/var/lib/opylitel-test`, `/var/lib/opylitel-ledger`. Файлы0600, каталоги0700. Учесть права самого администратора и хостера.
- РФ размещение основного сервера, БД, журналов, резервных копий и доступа подрядчиков документально подтвердить. Название Beget или IP сами по себе недостаточны. Нужны сведения провайдера и применимые поручения. Подтверждение географии/юридического оператора — отдельные блокеры реальных данных.
- Для теста ориентир: 1 vCPU, 1ГБ RAM, 2ГБ свободного места плюс ротация резервов; это инженерная оценка, не проверенный тариф/SLA. Без внешних БД/npm-пакетов во время запуска. Сборка архива требует Python3, тесты — Node24; браузерный QA дополнительно Playwright/Chromium.
- Типовой PHP shared-hosting не объявляется совместимым: нужно отдельно подтвердить постоянный Node24 процесс/прокси/закрытые каталоги. VPS/managed Node без подтверждения доступа не приобретается.

## Что находится в выпуске

app/ со всем серверным и клиентским кодом, локальной Leaflet/лицензией; `privacy.html` и `consent.html` с историческими неутверждёнными документами; manifest.json с SHA256 каждого файла. Нет баз, журналов, паролей, токенов, реальных заявок и runtime Node. Приложение всегда synthetic. Публичный noindex/запрет iframe сохранены.

## Установка ответственным администратором

1. Проверить SHA256 архива и внутренний manifest; извлечь в НОВЫЙ отдельный каталог релиза. Не распаковывать поверх current. Не использовать публичный document root. Не устанавливать общие nginx/CI/DNS без владельца сборки.
2. Создать закрытые каталоги данных/ledger/backup и персональный доступ TLS+auth_basic на отдельный тестовый vhost. Заменить example hostname/сертификаты в nginx примере. Конфиг `ru-synthetic.example.json` скопировать в `/etc/opylitel-test/config.json`, заполнить фактический HTTPSorigin и private paths. accessGate — требование, а НЕ доказательство работающего gateway.
3. Выполнить `node app/server/preflight.mjs /etc/opylitel-test/config.json` из распакованного релиза. Отчёт не показывает секретов. Он проверяет Node/SQLite/config/пути; не удостоверяет географию/TLS/gateway.
4. Первое открытие БД применяет локальные неизменяемые миграции0001/0002 с SHA256; старый r2 schema принимается idempotent baseline. Ошибка checksum/новая неизвестная миграция блокирует запуск. Изменять уже применённые SQL запрещено. Для будущих миграций — новый файл и проверка совместимости/отката.
5. После `nginx -t` и разрешённой настройки отдельного unit запустить сервис. Проверить извне anonymous `/`, `/api/fields`, `/api/health`, assets:401, содержимое не раскрыто; owner-auth200; wrongHost421; Secure+HttpOnly+SameSite cookie; `/api/intake`503. Секреты не писать в командную строку/скриншоты/доказательства.
6. Прогнать синтетический сценарий: два поля, draft скрыт, чужие IDs, публикация/фильтры2027/закрытие, touchUI, восстановление. До отдельной приёмки это NOT_VERIFIED на российском сервере.

## Резервирование и восстановление

Online snapshot: `node app/server/maintenance.mjs backup /private/demo.sqlite /private/backup.sqlite /private/deletions.jsonl`. Используется SQLite backup API, проверка integrity, SHA256 sidecar manifest, закрытый временный файл и rename. Копировать живой файл напрямую запрещено.

Каждое удаление сначала синхронно записывает намерение в отдельный JSONL ledger с fsync, затем удаляет запись/фиксирует tombstone в БД. Сбой после записи намерения трактуется консервативно: старт/restore применит удаление, даже если HTTP-ответ не дошёл. Ledger не содержит текста анкеты и контактов. Если ledger повреждён — старт/restore блокируются. Учитывать копии и права/срок хранения самого ledger.

Ledger должен сохраняться/копироваться независимо от старых backup, иначе потеря ОБОИХ носителей неразрешима. Размещение в другой папке на том же диске само по себе не даёт независимости. Согласовать долговечный РФ backup/mirror и требуемый RPO для ledger до рабочего использования. Если после полной потери ledger нет — восстановление базы НЕ разрешено автоматически: нельзя доказать, что удаления не воскреснут.

Restore: остановить unit; убедиться в отсутствии активной `.lock`; `node app/server/maintenance.mjs restore /private/demo.sqlite /private/backup.sqlite /private/deletions.jsonl`. Lock не удалять вслепую: PID файла может требовать проверки после аварии. Подтверждённый stale lease удаляет только администратор при остановленном процессе. Копия и manifest проверяются ДО изменения основного файла; stage проходит миграции/применение ledger/очистку sessions/integrity; только затем заменяется основной путь. Старая БД остаётся как закрытая before-restore копия для расследования, её уничтожение/срок отдельно контролируются. После восстановления выполнить сценарий проверки и новый вход.

## Откат релиза

Сначала остановить сервис и сделать проверенную копию БД+независимого актуального ledger; сохранить текущий release ID и config. Переключить current на предыдущий неизменённый релиз ТОЛЬКО при совместимой схеме; более старый сервер откажется от неизвестной миграции. Для несовместимой схемы — сначала проверенный backup restore с актуальным ledger, не DROPтаблиц и не автоматический down.sql. Откат не должен возвращать удалённые записи. Без предыдущего релиза/проверенной копии откат считается BLOCKED, а не «готов».

## Ограничения

Production аккаунты/MFA/модераторский чат/экстренные уведомления/проверка юроснований остаются не приняты. nginx/systemd примеры не установлены и синтаксически на российской машине не проверены. Обращения Beget от0-0 не дублировались. Единственный требуемый следующий доступ: подтверждённая отдельная РФ тестовая площадка с постоянным Node24 процессом и закрытым TLSgateway под управлением владельца хостинга; затем install/preflight/smoke по этому документу. Никаких реальных анкет/полей.

## Воспроизводимый выпуск и исполняемый переключатель

`python3 app/deploy/package-release.py /private/opy-r3.tar.gz` создаёт детерминированный tar.gz. `python3 app/tests/release-check.py` проверяет два одинаковых архива, manifest и тесты из распакованного кода. Evidence не включается в runtime-архив; доступно отдельно в PR.

Stage: `python3 app/deploy/release-control.py stage /private/opy-r3.tar.gz /opt/opylitel-test/releases --sha256 ПОДТВЕРЖДЕННЫЙ_SHA256`. Проверяются hash, пути/лимиты/дубликаты, manifest; существующий релиз не перезаписывается.

После остановки сервиса: `python3 app/deploy/release-control.py activate /opt/opylitel-test/current /opt/opylitel-test/releases/opy-ru-synthetic-r3 /etc/opylitel-test/config.json /private/backups --server-stopped`. Скрипт требует отсутствия lease, выполняет preflight, read-only проверку совместимости миграций, backup и атомарно переключает symlink. Сам сервис не запускает.

Rollback использует ту же команду с `rollback` и подтверждённым предыдущим каталогом. Без совместимой БД откажется; отдельный restore с актуальным ledger выполняется осознанно до повторного переключения. Флаг --server-stopped не заменяет проверки администратора, а lease не удаляется автоматически. Примеры путей должны быть заменены на фактические.

В этой среде systemd unit прошёл static verify после подстановки фактического Node binary/каталога; это не установка. В исходном шаблоне `/usr/bin/node` требует подтверждения на целевой машине. Nginx binary здесь отсутствует — `nginx -t` NOT_RUN.
